# Verification against the real game (plan §9)

This is the record of the Tier C verification: the real CS:GO server is driven with the same command
streams as the `movement` crate, and the two are compared tick by tick. Results are in the status
table in `README.md`; resolved mismatches are in `docs/divergences.md`.

## What was measured

| | |
|---|---|
| Game | CS:GO 1.38.8.1 (`csgo_legacy`, ServerVersion 1575, final legacy build). Dedicated server: SteamCMD app 740 |
| Server plugins | MetaMod:Source 1.11.0-git1163, SourceMod 1.12.0-git7255, `csmove_capture` 1.0.0. KZ runs add GOKZ 3.6.4 (core and the three mode plugins only) and MovementAPI 2.4.4 |
| Map | `csmove_capture`: the test level from `crates/testlevel`, exported by `compare map` and compiled with the CS:GO SDK's vbsp/vvis/vrad. Geometry is identical by construction; the level hash is stored in every capture |
| Driven player | A real CS:GO client on the same machine, connected over the LAN address. The plugin replaces its `buttons`, move values and view angles in `OnPlayerRunCmd`, so nobody touches the client |
| Logged | Per command, a `pre` row (before `PlayerRunCommand`) and a `post` row (after it): origin, velocity, base velocity, eye angles, ground entity, flags, move type, `m_bDucked`, `m_bDucking`, duck amount, duck speed, stamina, max speed, fall velocity, old buttons, ladder normal. Every float is logged as decimal and as raw bits. `m_surfaceFriction` is not exposed in CS:GO's datamaps and is not compared |
| Scenarios | The ladder in plan §9.5, generated by `compare scenarios` (fixed scripts, plus closed-loop ones whose commands are chosen by our model and then frozen): about 77 at 64 tick and 79 at 128 tick, with repeats far from the map origin (`S1F`, `S4F`, `S7F`) |

## Running it

```powershell
# once: CS:GO legacy client, SteamCMD app 740 server, CS:GO SDK (app 745), the MetaMod/SourceMod
# (and optionally GOKZ/MovementAPI) zips in one folder
powershell -File tools\capture\setup.ps1 -Server D:\Programs\csgo_ds -Mods D:\Programs\csgo_mods `
    -Sdk D:\Programs\csgo_sdk\bin -Game "D:\SteamLibrary\steamapps\common\Counter-Strike Global Offensive"

# one batch: starts srcds and the client, runs list_<mode>_<tickrate>.txt, imports the captures
powershell -File tools\capture\run.ps1 -Server D:\Programs\csgo_ds -Tickrate 64 -Out data\captures\raw\v64

cargo run --release -p compare -- all data\captures\raw\v64 --reports reports\v64   # summary + per-capture reports
cargo run --release -p compare -- trace data\captures\raw\v64\<capture> 57..60       # our routine-level events, re-synced
cargo run --release -p compare -- repro <capture-a> <capture-b>                      # reproducibility
cargo run --release -p compare -- promote <capture> crates\movement\tests\captures   # regression test
cargo run --release -p app -- --ghost <capture>                                       # in-app ghost overlay
```

Each report (`reports/<run>/<capture>/`) has `report.txt` (verdict, per-column counts, first divergence
with surrounding state, command and events, phase check), `residuals.csv`, `residuals_resync.csv`, and
`report.html` with speed, z and error plots.

## Rig findings (not movement divergences)

- **Bots can't be the subject.** CS:GO bots crouch while jumping on their own (the server ducks them on
  the jump command even with `IN_DUCK` overridden off), so captures drive a real client. `-Bot` remains for
  rig debugging.
- **Leftover state between runs.** Fall damage leaves a recovering `m_flVelocityModifier` that scales the
  next run's acceleration (found as a ×0.96 first-tick speed). The plugin resets health and stamina at the
  teleport and the modifier on every settle tick: the first run after the client joins showed the same
  ×0.96 even after a teleport-time reset.
- **Respawning a live player hangs srcds** (`CS_RespawnPlayer` on an alive bot spun forever); the plugin
  respawns only dead players. The weapon-strip loop is bounded (`RemovePlayerItem` can refuse).
- **Dropped or repeated commands.** A real client occasionally produces a repeated command number right
  after loading; the plugin detects any non-consecutive `cmdnum`, discards the run and retries it
  (plan §9.4). Server ticks may hold two commands, so only command numbers are checked.
- **Loading.** The client defers `+connect` at startup and never runs it, and loopback (`127.0.0.1`) never
  answers on this build; `run.ps1` connects through the client's `-netconport` using the LAN address. The
  client also needs the map and its nav file locally (uploads are off). With GOKZ loaded the first join
  takes a few minutes.
- **SourceMod 1.12 is required for KZ runs.** MovementAPI 2.4.4 (and so GOKZ) refuses to load on
  SourceMod 1.11 ("code is too new"). SourceMod only injects and logs, so this doesn't affect results.
- **GOKZ API.** The mode is set with `GOKZ_SetMode(client, mode)` (Vanilla 0, SimpleKZ 1, KZTimer 2). It
  returns false when nothing changes, because GOKZ remembers each client's mode, so the plugin checks
  `GOKZ_GetOption(client, "GOKZ - Mode")` instead. At 64 tick the mode stays Vanilla whatever is asked.
  GOKZ's surf-fix plugin (`gokz-momsurffix`) changes collision and is deliberately not installed.
- **One batch at a time.** Two `run.ps1` loops running at once fight over the server and client ports
  (runs time out with no player, or fail on locked logs). Kill leftover `srcds`/`csgo` processes before a
  new batch.
- **Reproducibility (plan §9.7 step 1):** 75 scenarios captured in two separate server sessions are
  bit-identical, pre and post rows.

## Results

See the status table in `README.md` for the per-subsystem verdict against plan §9.9, and
`docs/divergences.md` for every resolved and open mismatch.

### Per-mode runs (M-*, GOKZ 3.6.4)

| Scenario set | KZTimer 128 | SimpleKZ 128 |
|---|---|---|
| S4, S4F standing jumps | BIT_EXACT | BIT_EXACT |
| S5 strafe jump | WITHIN_EPS | WITHIN_EPS |
| S7, S7F ten perfect bhops | BIT_EXACT | WITHIN_EPS (after the SimpleKZ takeoff snap, D10) |
| S19 long jumps (230/240/250) | BIT_EXACT | BIT_EXACT |
| S20 prestrafe while turning | **FAILED** from the first turning tick | **FAILED** from the first turning tick |

- Everything except prestrafe matches: GOKZ's cvars (air accelerate 100, bunnyhopping on, no stamina),
  perfect-bhop handling and takeoff behavior are reproduced by our mode configs and hooks.
- Prestrafe does not match. Both real modes reach about 276 as the reference says, but KZTimer peaks near
  275.6 and then decays while still turning (272 after 0.7 s, 260 after 1 s) where ours holds 276, and
  SimpleKZ caps at 276.54 (ours 276.0) and grows more slowly than our design. Matching it exactly means
  implementing GOKZ's prestrafe algorithms, which are GPL-3.0; CLAUDE.md requires a licence decision
  before porting GOKZ logic, so this is left open (D10).
- KZTimer at 64 tick could not be captured: GOKZ 3.6.4 keeps the player in Vanilla mode at 64 tick
  (`GOKZ_SetMode` has no effect), so our KZTimer-at-64 combination has no real counterpart.
- Vanilla S20 (turning while running, then a jump) is BIT_EXACT at 64 tick and WITHIN_EPS at 128.
