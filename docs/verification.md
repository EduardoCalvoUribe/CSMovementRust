# Verification against the real game (plan §9)

This is the record of the Tier C verification: the real CS:GO server is driven with the same command
streams as the `movement` crate, and the two are compared tick by tick. Results are in the status
table in `README.md`; resolved mismatches are in `docs/divergences.md`.

## What was measured

| | |
|---|---|
| Game | CS:GO 1.38.8.1 (`csgo_legacy`, ServerVersion 1575, final legacy build). Dedicated server: SteamCMD app 740 |
| Server plugins | MetaMod:Source 1.11.0-git1163, SourceMod 1.12.0-git7255, `csmove_capture` 1.0.0. KZ runs add GOKZ 3.6.4 (core and the three mode plugins only) and MovementAPI 2.4.4 |
| Map | `csmove_capture`: the test level from `crates/testlevel`, exported by `compare map` and compiled with the CS:GO SDK's vbsp/vvis/vrad. Geometry is identical by construction; the level hash is stored in every capture |
| Driven player | A real CS:GO client on the same machine, connected over the LAN address. The plugin replaces its `buttons`, move values and view angles in `OnPlayerRunCmd`, so nobody touches the client |
| Logged | Per command, a `pre` row (before `PlayerRunCommand`) and a `post` row (after it): origin, velocity, base velocity, eye angles, ground entity, flags, move type, `m_bDucked`, `m_bDucking`, duck amount, duck speed, stamina, max speed, fall velocity, old buttons, ladder normal, and (since the edgebug sweep) health, `m_flVelocityModifier` and the active weapon. Every float is logged as decimal and as raw bits. `m_surfaceFriction` is not exposed in CS:GO's datamaps and is not compared |
| Scenarios | The ladder in plan §9.5, generated by `compare scenarios` (fixed scripts, plus closed-loop ones whose commands are chosen by our model and then frozen): about 77 at 64 tick and 79 at 128 tick, with repeats far from the map origin (`S1F`, `S4F`, `S7F`) |

## Running it

```powershell
# once: CS:GO legacy client, SteamCMD app 740 server, CS:GO SDK (app 745), the MetaMod/SourceMod
# (and optionally GOKZ/MovementAPI) zips in one folder
powershell -File tools\capture\setup.ps1 -Server D:\Programs\csgo_ds -Mods D:\Programs\csgo_mods `
    -Sdk D:\Programs\csgo_sdk\bin -Game "D:\SteamLibrary\steamapps\common\Counter-Strike Global Offensive"

# one batch: starts srcds and the client, runs list_<mode>_<tickrate>.txt, imports the captures
powershell -File tools\capture\run.ps1 -Server D:\Programs\csgo_ds -Tickrate 64 -Out data\captures\raw\v64

cargo run --release -p compare -- all data\captures\raw\v64 --reports reports\v64   # summary + per-capture reports
cargo run --release -p compare -- trace data\captures\raw\v64\<capture> 57..60       # our routine-level events, re-synced
cargo run --release -p compare -- repro <capture-a> <capture-b>                      # reproducibility
cargo run --release -p compare -- promote <capture> crates\movement\tests\captures   # regression test
cargo run --release -p app -- --ghost <capture>                                       # in-app ghost overlay
```

Each report (`reports/<run>/<capture>/`) has `report.txt` (verdict, per-column counts, first divergence
with surrounding state, command and events, phase check), `residuals.csv`, `residuals_resync.csv`, and
`report.html` with speed, z and error plots.

## Rig findings (not movement divergences)

- **Bots can't be the subject.** CS:GO bots crouch while jumping on their own (the server ducks them on
  the jump command even with `IN_DUCK` overridden off), so captures drive a real client. `-Bot` remains for
  rig debugging.
- **Leftover state between runs.** Fall damage leaves a recovering `m_flVelocityModifier` that scales the
  next run's acceleration (found as a ×0.96 first-tick speed). The plugin resets health and stamina at the
  teleport and the modifier on every settle tick: the first run after the client joins showed the same
  ×0.96 even after a teleport-time reset.
- **Respawning a live player hangs srcds** (`CS_RespawnPlayer` on an alive bot spun forever); the plugin
  respawns only dead players. The weapon-strip loop is bounded (`RemovePlayerItem` can refuse).
- **Dropped or repeated commands.** A real client occasionally produces a repeated command number right
  after loading; the plugin detects any non-consecutive `cmdnum`, discards the run and retries it
  (plan §9.4). Server ticks may hold two commands, so only command numbers are checked.
- **Loading.** The client defers `+connect` at startup and never runs it, and loopback (`127.0.0.1`) never
  answers on this build; `run.ps1` connects through the client's `-netconport` using the LAN address. The
  client also needs the map and its nav file locally (uploads are off). With GOKZ loaded the first join
  takes a few minutes.
- **SourceMod 1.12 is required for KZ runs.** MovementAPI 2.4.4 (and so GOKZ) refuses to load on
  SourceMod 1.11 ("code is too new"). SourceMod only injects and logs, so this doesn't affect results.
- **GOKZ API.** The mode is set with `GOKZ_SetMode(client, mode)` (Vanilla 0, SimpleKZ 1, KZTimer 2). It
  returns false when nothing changes, because GOKZ remembers each client's mode, so the plugin checks
  `GOKZ_GetOption(client, "GOKZ - Mode")` instead. At 64 tick the mode stays Vanilla whatever is asked.
  GOKZ's surf-fix plugin (`gokz-momsurffix`) changes collision and is deliberately not installed.
- **One batch at a time.** Two `run.ps1` loops running at once fight over the server and client ports
  (runs time out with no player, or fail on locked logs). Kill leftover `srcds`/`csgo` processes before a
  new batch.
- **Runs that started at 0.96 speed.** Some runs accelerated by exactly 0.96 of ours from the first
  command (`S1`, `S17-jumpbug-256` in v64a, several `S16t-*` in the first edgebug batches), with health
  100 and `m_flVelocityModifier` 1. 0.96 is 240/250, a pistol's speed against the knife's, and the runs
  followed a client join or a respawn. The plugin now retries any run that doesn't start with the knife
  active (it logs the active weapon). No run has started slow since. It also clears the fall velocity at
  the teleport, so a run that ended in mid-air can't make the next settle land with fall damage.
- **Lethal runs are discarded.** A run where the player dies is retried and finally dropped (`player
  dead, giving up`), so scenarios must not end in a fall from the edgebug tower to the floor. The
  threshold scenarios stop just below the platform when they miss, and 0.1 s after an edgebug or
  landing. That way a real-game miss is compared instead of discarded.
- **Reproducibility (plan §9.7 step 1):** 75 scenarios captured in two separate server sessions are
  bit-identical, pre and post rows.

## Results

See the status table in `README.md` for the per-subsystem verdict against plan §9.9, and
`docs/divergences.md` for every resolved and open mismatch.

### Per-mode runs (M-*, GOKZ 3.6.4)

| Scenario set | KZTimer 128 | SimpleKZ 128 |
|---|---|---|
| S4, S4F standing jumps | BIT_EXACT | BIT_EXACT |
| S5 strafe jump | WITHIN_EPS | WITHIN_EPS |
| S7, S7F ten perfect bhops | BIT_EXACT | WITHIN_EPS (after the SimpleKZ takeoff snap, D10) |
| S19 long jumps (230/240/250) | BIT_EXACT | BIT_EXACT |
| S20 prestrafe while turning | WITHIN_EPS (horizontal columns bit-exact) | WITHIN_EPS (horizontal columns bit-exact) |

- Everything matches since the KZ modes were ported from GOKZ 3.6.4 and MovementAPI 2.4.4 (D10,
  `docs/modes-notes.md`); the only residual in S20 is one landing `origin_z` tick (2.4e-7), the open
  landing difference. Before the port, our own hook designs matched jumps, bhops and long jumps but not
  prestrafe: real KZTimer peaks near 275.6 then decays while still turning, and SimpleKZ caps at 276.54.
- KZTimer at 64 tick has no real counterpart: GOKZ's KZTimer and SimpleKZ refuse to run below 128 tick
  (so GOKZ kept the player in Vanilla), and our KZ modes now lock 128 tick too.
- Vanilla S20 (turning while running, then a jump) is BIT_EXACT at 64 tick and WITHIN_EPS at 128.

### D14 probes (64 tick)

Ten scenarios (`D14-*` in `compare scenarios`), each changing one factor of `S17` (place, held keys,
horizontal speed, duck timing, ground or air), isolated the faster duck-speed recovery: it starts once
the player is more than 64 units horizontally from where duck speed was last full. Rule, evidence and
fix: `docs/divergences.md` D14. After the fix both 64-tick S17 captures are BIT_EXACT; BIT_EXACT counts
went from 45 to 47 of 77 (v64b) and 44 to 45 (v64a), with no new failures in any run.

### Edgebug thresholds (S16t)

`compare scenarios` scans the run yaw off the edgebug tower for three approaches (jump at the edge, run
off it, shift-walk then jump). At each switch between landing on the platform, an edgebug at its edge,
and missing it, the yaw is narrowed to two adjacent f32 values, one on each side [Ref §14]. Both
become scenarios, so the real game has to put each run on the same side of a threshold that is one ULP
of yaw wide. Fall damage is compared too: the comparator adds a `Damage` event from the logged health
(ours: a landing faster than 580 units/s), so an "edgebug" that hurt the player fails the event check.

| Batch | 64 tick | 128 tick | |
|---|---|---|---|
| First sweep (Quake leave rule) | near side (land/edgebug) exact; far side (edgebug/miss): real edgebugs where we missed | same | found D21 |
| After D21 (touch-time rule), sweep regenerated, then captured | 13/13: 12 BIT_EXACT + S1 | 13/13: 11 BIT_EXACT, 2 WITHIN_ULP | prediction confirmed |

All 24 threshold captures are promoted (`S16t-*`). No real edgebug took damage. The landing side
of each threshold was right from the start: it is decided by the ground probe after the hit, not by
the trace.

### Pixelsurf candidates (P19)

Four lanes beside 512-unit towers (Shift+5–8 in the app): a wall of 8-unit slabs, a wall of 1-unit
slabs between 256 and 384 listed bottom-up, the same listed top-down, and a wall with 1, 2 and 4 unit
ledges. The community recipe is to press flush against a wall (a coordinate shows `.00`, reached by
alternating strafes into it with W held) and to reach a "wireframe" height at a tick boundary.

- `P19-*`: running off each lane and pressing into the wall while falling past its seams, three ways,
  at both tick rates. Real game and model agree: no glide.
- `P19s-*`: inputs found by searching our model with the unclamped enter fractions of SDK 2013
  (D22), which made the player glide on the top-down lane for up to 230 commands. The real game didn't
  glide on either lane, so that rule was reverted. With the current model, all 12 match the real game.

So stacked box brushes alone don't produce pixelsurfs, even with the hull within 0.0005 of the wall
and the feet within 1/32 above a seam. Untested: non-axial brushes (whose BSP bevel planes are traced by
the general routine), displacements (D19), and seams between brushes that aren't flush. All need new
test geometry or a community map with a known pixelsurf.

### BSP maps (M9)

- **Compiled test map through the BSP backend.** `compare all <run> --bsp data\map\csmove_capture.bsp`
  replays every capture on the map the server actually ran, loaded by `world/bsp.rs`: the same verdict
  for all 77 captures at 64 tick and 79 at 128 tick, with the same BIT_EXACT counts as the primitive
  world. `cargo test` repeats this for the promoted captures when the compiled map is present.
- **A community KZ map.** kz_longjumps_v4096 (Steam Workshop 1707360214, fetched with SteamCMD, kept
  outside the repository). `compare scenarios <dir> --bsp <map> --lj x,y,z,yaw` generates long jumps on
  its 240-unit blocks with our model (strafe timing searched until the jump lands on the next block);
  `run.ps1 -MapFile <map>` captures them, with GOKZ's jumpstats loaded in the KZ modes.

| Mode, 128 tick | Movement vs real game | Our LJ distance | GOKZ in-game LJ |
|---|---|---|---|
| KZTimer, 3 lanes | BIT_EXACT | 266.6992 | 266.6992 (one 266.6991) |
| SimpleKZ, 3 lanes | BIT_EXACT | 266.6992 | 266.6992 |
| Vanilla, 3 lanes | WITHIN_EPS | 247.5244 / 247.5239 | (GOKZ not loaded) |

  This meets the M9 gate (long-jump distances on a known KZ map equal the in-game jumpstats for the same
  input) and resolves D11. Earlier batches on the same map also gave BIT_EXACT KZ-mode runs that fell
  into the pit (a scenario-generator strafe bug, since fixed: for air accelerate 100 the best strafe is
  perpendicular to the velocity).
- **Rig findings.** A start with the hull exactly touching a wall or the map's start button is inside
  solid for both simulations; the engine then frees the player with `CheckStuck`, which we don't model
  (D20). A capture made while the machine was busy compiling had four commands processed in one server
  tick with no movement (server tick 6943 to 6950, consecutive command numbers); keep the machine idle
  during captures. KZ runs need `gokz-jumpstats` installed (setup.ps1 now does), and its reports are in
  the client console log that `run.ps1` copies next to the captures.
